What the numbers mean, and what they do not.

The requirement is stated as a single number for a 1080p frame pair, and the cost of a delta
follows the size of the change, not the size of the frame. The asserted profile changes two
elements per frame, which is what a desktop does when a clock ticks and a label updates. The
large profile changes about half the screen in one frame, which is a scroll of a dense list or
a full-screen repaint, and it costs about 37 ms because labelling connected components is
linear in the number of changed pixels. Both numbers are recorded rather than one, because a
single figure would describe neither. The limitation is stated in docs/vv/results.md and in
the report's threats to validity.

How the target was reached. The first measurement of this harness failed:

  mean 23.40 ms, p95 25.26 ms, p99 29.27 ms

Three causes, found by benchmarking the stages rather than guessing:

1. The luma conversion ran six million times per frame pair. The comparison converted both
   frames and the fingerprint converted one of them again. The differ now keeps the two most
   recent luma planes and both passes read them, so the conversion runs once per frame:
   plane 6.7 ms per pair to 3.8 ms.
2. The fingerprint summed every pixel of every cell, a second full walk over the frame at
   2.8 ms. Cell values are now sampled, at a stride of a quarter of a cell in each axis, which
   is a sixteenth of the work and measures the same thing for a fingerprint that is compared
   with tolerance: 2.8 ms to 0.05 ms. Fusing the accumulation into the conversion pass was
   tried first and measured slower, 8.2 ms against 6.7 ms, because the per-pixel cell index
   cost more than the second pass it replaced. The slower version was reverted.
3. The comparison walked the whole mask to find component starts and walked every pixel of
   every changed row. It now scans only rows that changed and skips eight bytes at a time
   within a row: 4.2 ms to 2.7 ms.

A fourth idea, unrolling the conversion loop four pixels per iteration, measured 2 percent
faster and was reverted: twelve lines of duplicated index arithmetic for 0.08 ms is not a trade
worth making.

Contention. The suite runs test packages in parallel, so a latency run inside `go test ./...`
competes for the CPU and produces a tail that belongs to the machine. The measurement detects
that by comparing the median against the fastest pair and skips with a message rather than
reporting a contended number as the engine's. The numbers above come from `make perf`, which
runs with -p 1 and nothing else running.
