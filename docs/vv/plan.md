# Verification and validation plan

Section 5 of the report is graded on this plan and on the evidence it produces.
The plan is written before implementation, and the audit log is filled in as
flaws are found rather than reconstructed at the end.

## Scope

Verification asks whether the system was built correctly against
`specs/001-<slug>/spec.md`. Validation asks whether it solves the problem for its
stakeholders. Both are required: a system can pass every unit test and still fail
its users.

## Levels and techniques

| Level | Technique | Tooling | Evidence |
|---|---|---|---|
| Unit | Tests written from the specification before the implementation, one test per requirement branch | TBD with the stack | `tests/`, `docs/vv/results.md` |
| Integration | Tests across module and storage boundaries, including failure paths | TBD with the stack | `tests/`, `docs/vv/evidence/` |
| Functional | The `quickstart.md` scenarios from `specs/001-<slug>/` executed end to end | TBD with the stack | `docs/vv/evidence/` |
| Requirement verification | Each `FR-###`, `NFR-###` and `SC-###` has a row in `docs/traceability.md`; a row marked in-progress or verified names a real task entry, and a verified row names existing test and evidence files | `make check` | `docs/traceability.md` |
| Non-functional | Measurements against the targets in `NFR-###`: latency, concurrency, coverage, dependency audit | TBD with the stack | `docs/vv/evidence/` |
| User acceptance | Stakeholder walks through the primary user stories against the acceptance scenarios | Manual script in `docs/vv/acceptance.md` | Written outcome per scenario |
| Compliance | No secret in the repository, dependency licences acceptable, personal data handling as specified | `gitleaks` or equivalent, `pip-audit` or equivalent | CI log in `docs/vv/evidence/` |

## Threats to validity

| Threat | How it is reduced |
|---|---|
| Tests generated by the same model that wrote the code share its blind spots | Tests are written from `spec.md` before implementation. Because the project is solo, they are then reviewed in a separate pass, and an independent agent review in a fresh context is briefed to falsify them rather than confirm them |
| Coverage measured on generated tests only | Coverage is reported per module and reviewed for the domain layer specifically |
| Test data chosen to make the implementation pass | Edge cases come from the spec's own Edge Cases section, not from the code |
| Acceptance tested by the author | The acceptance script is executed by people who are not the author, recruited before implementation starts, and the outcome is committed |
| Non-functional targets measured on a developer machine only | Targets are stated with the environment in which they were measured |

## Traceability

`docs/traceability.md` is the single matrix. `python3 scripts/check_traceability.py`
verifies that every requirement defined in a specification has a row, that a row
marked `in-progress` or `verified` names a task entry in the feature's `tasks.md`
which owns that requirement, and that a row marked `verified` names a test file
and an evidence file that exist inside the repository. A verification claim
therefore cannot rest on a file that does not exist, and a task cannot be a
passing mention in prose.

Values the check cannot judge, such as a command string or an external URL, warn
rather than fail, so a warning is a prompt to look rather than a pass. Three limits
are inherent and are stated in `docs/traceability.md`: the check cannot tell
whether an existing test exercises the requirement, a `planned` row may name
neither a task nor a test, and requirement definitions inside fenced code blocks
are ignored because they are examples. Run `make check-strict` once the first
specification exists.

## Definition of done for a feature

1. Every requirement in the feature's `spec.md` is `verified` in the matrix, or is
   recorded as `deferred` or `withdrawn` with the reason stated in the report.
2. `make check` passes.
3. The feature's `quickstart.md` scenarios were executed and their output saved.
4. Every flaw found during review has an audit log entry with a fixing commit.
5. The prompt log contains the session that produced the feature.
