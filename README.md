## What it does

ScreenDelta reads consecutive screen frames and reports what changed between them:

- **where** the change is, as a rectangle normalized to the frame;
- **what happened**, as `added`, `changed`, `moved` or `removed`;
- **which element it is**, as an identifier that stays stable while that element is
  tracked and is never reused within a session;
- **how strong that claim is**, as a confidence and an explicit uncertainty marker
  for an element the engine will not claim to have matched.

It runs one CPU core, needs no network, and emits one self-contained JSON document per
frame. It is deliberately one stage of a pipeline rather than a whole tool: it does not
classify elements, recognise text or drive a pointer. What it adds is a contract a
planner can build on, including the honest parts.

## Use it in two minutes

```bash
git clone <this repository> && cd swcon2627-project
make build                                  # builds bin/screendelta
go run ./tools/corpusgen --case changed-label --out /tmp/frames
                                            # or use two of your own screenshots
bin/screendelta diff --previous /tmp/frames/001.png --current /tmp/frames/002.png
```

That prints one JSON document describing the change. To process a whole sequence,
including the identity of each element across frames:

```bash
bin/screendelta stream --source /tmp/frames          # one document per frame, per line
bin/screendelta diff --help                          # every option, and the exit codes
```

Frames may be PNG files or raw RGBA with `--width` and `--height`. A configuration
document can restrict the output to regions of interest, ignore parts of the screen such
as a clock, and set the noise floor. `specs/001-frame-delta-engine/quickstart.md` lists
nine scenarios with the exact commands and the expected result.

## The workflow

Spec Kit is run in this order. Steps marked as gates must not be skipped.

```
/speckit.constitution    project rules, written once, amended deliberately
/speckit.specify         spec.md, from the feature description
/speckit.clarify         resolves open questions in spec.md          (gate)
/speckit.plan            plan.md, research.md, data-model.md, contracts/, quickstart.md
/speckit.checklist       reviewer-owned quality checklists           (gate)
/speckit.tasks           tasks.md, ordered and dependency-aware
/speckit.analyze         read-only cross-artifact consistency report (gate)
/speckit.implement       code, task by task
/speckit.converge        appends remaining work as tasks
```

`CONTRIBUTING.md` defines the gates, the commit convention and the review rules.
`AGENTS.md` defines the same rules for coding agents.

## Quickstart

Prerequisites: `git`, Python 3.11 or newer (Spec Kit requires it), and `uv`.
Spec Kit is pinned to the version this repository was scaffolded with, so every
member generates the same files.

```bash
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git@v1.0.12
specify --version          # expect 1.0.12
specify integration status # shows the installed agent surfaces
```

Command surfaces installed in this repository:

| Agent | Commands |
|---|---|
| GitHub Copilot in VS Code | `.github/prompts/speckit.*.prompt.md` and `.github/agents/speckit.*.agent.md`, recommended in `.vscode/settings.json` |
| opencode | `.opencode/commands/speckit.*.md` |
| dsh | `.dsh/skills/speckit-*/SKILL.md` |

Checks:

```bash
make check        # requirement traceability: every requirement defined in specs/
                  # has a matrix row; an in-progress or verified row must name a
                  # task entry in tasks.md, and no other entry may own that
                  # requirement; a verified row must name an existing test file and
                  # an existing evidence file inside the repository. A planned row
                  # may name neither, by design. A command string or an external
                  # URL warns instead of failing.
make check-strict # the same, and fails while no specification exists
make help         # list targets
```

CI runs the traceability check on every push, and the cross-build for three targets, so a repository whose
requirements are not traced or whose Windows build is broken fails rather than passing quietly. The report check
and the mutation and regression checks are local gates, run by `make check-strict` and the two scripts.

## Portability

The engine builds and runs on Linux and Windows from the same source, with no C
dependency and no platform-specific code. `make cross` builds both, which is what CI
checks; running the test suite on a Windows machine is outstanding and is listed under
[Open work](#open-work).

## Open work

1. **Acceptance testing with external testers** (NFR-007, SC-005). The script is
   `docs/vv/acceptance.md` and it has not been run, so the usability criterion is
   unverified. This is the one item no amount of agent work can close.
2. **An oversized frame is not refused.** A frame larger than the machine's memory fails when it is allocated
   rather than being rejected on its size, because a size limit is a configuration surface the specification does
   not ask for. `docs/analysis/converge-2026-09-27.md` records it as a gap with that reason.
3. **A Windows smoke test.** The cross-build is checked; running the suite on Windows is not.
4. **Cross-host determinism** (NFR-004). Output is byte-identical across thread counts
   on this host; another host and another Go version are untested.
5. **The final numbers pass.** Every count and measurement in the report and this file is
   regenerated from the repository before submission, since each further commit moves them.
